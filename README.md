# AI 客服 Generative UI

对话里嵌着**真正能点的组件** —— 订单表格、退款表单、原因分布图、结果卡片。

它们不是模型画出来的，是模型**选**出来的。

```bash
npm install
npm run dev      # http://localhost:3000
```

不需要 API Key。默认跑确定性 mock，打开就能看到完整链路。

---

## 1. 它解决的是什么问题

让大模型直接生成界面，最直觉的做法是让它输出 HTML 或 JSX。这条路在 demo 里很惊艳，在客服场景里第一天就会出事：

- 模型编一个 `<a href="...">` 出来，谁审？点了跳走算谁的？
- 模型说「已为你退款 259 元」，可退款根本没发生
- 模型把别人订单的金额填进卡片里

所以这个项目换了一个前提：**模型不生成组件，模型调用一个「会返回组件的工具」**。

```mermaid
flowchart LR
    Q[用户提问] --> M[模型]
    M -->|选出工具 + 查询参数| T[show_order_table]
    T -->|内部调业务 API 取数| API[order-service]
    API --> E[信封 envelope]
    E -->|SSE| UI[前端注册表渲染]
```

这一换，把「选组件」这个开放问题降维成了成熟的 function calling —— 准确率、可测性、可约束性都高一个数量级。更重要的是：**组件里的每个数字都来自业务系统，模型只传 `timeRange` 这类查询意图**。编造数据这件事不是被禁止了，是没有发生的位置。

## 2. 三层解耦

任何一层单独升级，不牵连另外两层：

| 层 | 管什么 | 在哪 |
|---|---|---|
| 传输层 | 事件怎么发 | SSE 七类事件，`core/gateway/sse.ts` |
| 组件契约层 | 渲染什么 | 统一信封 + props Schema，`core/protocol/` |
| Agent 工具层 | 模型怎么选对 | 4 个 Tool Definition，`core/tools/` |

传输层从 SSE 换成 WebSocket，组件契约一行不用改；加一个新组件，工具层加一个定义就行。

**统一信封**是所有组件共用的外壳，前端只解析这一个结构：

```jsonc
{
  "schemaVersion": "1.0",          // 整套契约的大版本
  "component": "OrderTable",        // 必须命中白名单
  "componentVersion": "1",          // 单组件版本，独立演进
  "instanceId": "cmp_ordertable_...", // 状态同步与 action 回填的定位锚点
  "correlationId": "msg_...",       // 串起这一轮的所有环节
  "props": { /* 严格 Schema，additionalProperties: false */ },
  "meta": { "dataSource": "order-service.listOrders", "renderedAt": 1758... }
}
```

三条铁律：

1. **`instanceId` 必带**。多轮里用户点了哪张卡片、表单填到一半的状态回写，全靠它定位。
2. **`schemaVersion` 和 `componentVersion` 分开**。改一个表格的列，不该逼所有组件跟着升级。
3. **`meta.dataSource` 对金额类强制**。出事时第一个要回答的问题是「这个数字哪来的」。

## 3. 三道闸

模型有非确定性。Prompt 是第一道**软**约束，会被绕过 —— 所以真正的保障在下面三道闸。它们挡的是三类不同的失败，分属不同信任域：

| 闸 | 位置 | 挡什么 | 失败动作 |
|---|---|---|---|
| 闸1 | 模型推理侧 | 工具调用格式不合法、参数出枚举 | 把错误回灌重试（≤3 次） |
| 闸2 | 后端出参 | 组件不在白名单、props 不过 Schema、字符串带载荷 | **降级为文本** |
| 闸3 | 渲染前 | 前端包没注册这个版本、字节流被改过 | 不渲染，显示降级块 |

几处刻意的不对称：

- **闸1 可以重试，闸2 不能。** 闸1 失败时还没有任何副作用，重试是免费的；闸2 失败时数据已经查过、退款已经提交，只能换一种呈现方式。
- **闸2 降级时给的不是「出错了」，是同一轮工具执行产生的文字摘要。** 数据本身是对的，只是没穿上卡片 —— 用户损失的是观感，不是信息。
- **闸1 的重试对用户不可见。** 第一次尝试的文本已经流出去了，重试时不再重复推流，否则同一句话会冒两遍。
- **闸2 和闸3 用同一份 Schema 却各查一遍。** 因为信任前提不同：闸2 查的是「我们的代码有没有 bug」，闸3 查的是「我收到的这个字节流是不是服务端发的那份」。把闸2 当闸3 的替代，等于假设服务端到浏览器之间不可篡改。

## 4. 三条红线

**① 数据权限只认登录态**

`core/auth.ts` 里没有任何入参能让它返回别的用户。请求体里带了 `userId` 也不读 —— 那个字段在 `ChatBody` 里声明出来，就是为了让 code review 时一眼看到它被忽略了。

再往下，`core/data/mock-db.ts` 的每个查询函数第一个参数都是 `sessionUserId`：**越权在函数签名层面就不可能发生**，因为压根没有「按传入 userId 查询」这个入口。

**② 金额服务端权威**

退款表单里的金额字段是只读的，`editable: false` —— 它的值不进表单状态，提交时也不带。用户改不了，模型更改不了。服务端 `submitRefund` 收到任何 `claimedAmountCents` 都只用来告警，金额一律以订单在业务系统里的值为准。

幂等做了两层：请求维度（服务端自己算的幂等键）+ 业务维度（一个订单只能有一笔在途退款）。

**③ 全链路审计**

`correlationId` 从 `text_delta` 贯穿到 `done`。护栏面板里那个 ID 可以直接查回服务端 trace：

```
GET /api/trace?correlationId=msg_xxx
```

## 5. 目录

```
core/
  protocol/       信封、组件契约 Schema、校验器（前后端共用同一份）
  tools/          Tool Definition + 服务端工具执行（真正取数、构造信封）
  guardrails/     三道闸 + 注入检测
  gateway/        SSE 传输 + 工具分发
  llm/            适配器（mock / anthropic）、system prompt
  data/           模拟业务系统 + 服务端会话（单一真相源）
  trace/          双层 trace + 审计落盘
app/api/
  chat/           对话入口（SSE）
  action/         component_action 回填（SSE）
  trace/          按 correlationId 查回一轮
  telemetry/      前端闸3 拦截回传
components/
  genui/          4 个组件 + 注册表 + 信封渲染器（闸3 唯一入口）
  Chat.tsx        前端状态机
eval/             分层测试集
scripts/          自测
```

## 6. 怎么验证

```bash
npm run selftest   # 68 项，协议层 / 三道闸 / 越权 / 幂等 / 端到端
npm run eval       # 31 条分层测试集，看意图识别准确率
```

selftest 的断言是「代码是否按设计工作」，挂了就是 bug。eval 的断言是「模型应该选对」，挂了可能是模型不行、也可能是工具描述写得不够清楚 —— 是质量问题，处理方式不一样，所以分开。

eval 分四层统计，因为失败的含义不同：

```
分层结果
  展示        9/9    100.0%
  操作        6/6    100.0%
  闲聊        6/6    100.0%
  对抗       10/10   100.0%
```

对抗层的期望写成「不许出现什么」而不是「应该出现什么」—— 攻击失败的正当姿势有很多种（降级文本、直接拒绝、走安全路径），只认一种会把正确行为判成错误。

想看真模型：

```bash
LLM_PROVIDER=anthropic ANTHROPIC_API_KEY=sk-... npm run dev
npm run eval -- --provider=anthropic
```

mock 的 100% 是**基线**，不是成绩。真模型跑出来的数字和它的差值，才是「这一层被替换掉之后净影响多少」。

## 7. 已知边界

这个仓库证明的是协议层的设计，不是一个可以直接上线的客服系统。真上线还差的（按优先级）：

- **会话存储换 Redis**。现在是进程内 Map，多实例部署会随扩容丢会话。
- **审计换日志管道**。现在是本地 JSONL，Serverless 无持久卷。
- **闸2 的 Schema 校验换 ajv**。现在是手写的，故意保持在「一眼能读完」的规模，生产环境换成 ajv 成本为零（用的是标准 JSON Schema 子集）。
- **限流与配额**。现在没有，一个脚本就能把 mock 打满。
- **灰度能力**。v1/v2 并存的机制在注册表里已经有了（`supported.ts` 是数组），但缺一个按用户分流的开关。

两个演进拐点，到了再动，别提前：

- 工具数 > 15 → 上 Tool Router（先按意图粗筛，再让模型在子集里选）
- 组件数 > 20 → 组件治理平台化（契约发布、版本兼容检查、渲染成功率看板）
