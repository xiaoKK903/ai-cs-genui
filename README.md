# AI 客服 Generative UI

对话里嵌着**真正能点的组件** —— 订单表格、退款表单、原因分布图、结果卡片。

它们不是模型画出来的，是模型**选**出来的。

```bash
npm install
npm run dev      # http://localhost:3000
```

不需要 API Key。默认跑确定性 mock，打开就能看到完整链路。

---

## 1. 它解决的是什么问题

让大模型直接生成界面，最直觉的做法是让它输出 HTML 或 JSX。这条路在 demo 里很惊艳，在客服场景里第一天就会出事：

- 模型编一个 `<a href="...">` 出来，谁审？点了跳走算谁的？
- 模型说「已为你退款 259 元」，可退款根本没发生
- 模型把别人订单的金额填进卡片里

所以这个项目换了一个前提：**模型不生成组件，模型调用一个「会返回组件的工具」**。

```mermaid
flowchart LR
    Q[用户提问] --> M[模型]
    M -->|选出工具 + 查询参数| T[show_order_table]
    T -->|内部调业务 API 取数| API[order-service]
    API --> E[信封 envelope]
    E -->|SSE| UI[前端注册表渲染]
```

这一换，把「选组件」这个开放问题降维成了成熟的 function calling —— 准确率、可测性、可约束性都高一个数量级。更重要的是：**组件里的每个数字都来自业务系统，模型只传 `timeRange` 这类查询意图**。编造数据这件事不是被禁止了，是没有发生的位置。

## 2. 三层解耦

任何一层单独升级，不牵连另外两层：

| 层 | 管什么 | 在哪 |
|---|---|---|
| 传输层 | 事件怎么发 | SSE 七类事件，`core/gateway/sse.ts` |
| 组件契约层 | 渲染什么 | 统一信封 + props Schema，`core/protocol/` |
| Agent 工具层 | 模型怎么选对 | 4 个 Tool Definition，`core/tools/` |

传输层从 SSE 换成 WebSocket，组件契约一行不用改；加一个新组件，工具层加一个定义就行。

**统一信封**是所有组件共用的外壳，前端只解析这一个结构：

```jsonc
{
  "schemaVersion": "1.0",          // 整套契约的大版本
  "component": "OrderTable",        // 必须命中白名单
  "componentVersion": "1",          // 单组件版本，独立演进
  "instanceId": "cmp_ordertable_...", // 状态同步与 action 回填的定位锚点
  "correlationId": "msg_...",       // 串起这一轮的所有环节
  "props": { /* 严格 Schema，additionalProperties: false */ },
  "meta": { "dataSource": "order-service.listOrders", "renderedAt": 1758... }
}
```

三条铁律：

1. **`instanceId` 必带**。多轮里用户点了哪张卡片、表单填到一半的状态回写，全靠它定位。
2. **`schemaVersion` 和 `componentVersion` 分开**。改一个表格的列，不该逼所有组件跟着升级。
3. **`meta.dataSource` 对金额类强制**。出事时第一个要回答的问题是「这个数字哪来的」。

## 3. 三道闸

模型有非确定性。Prompt 是第一道**软**约束，会被绕过 —— 所以真正的保障在下面三道闸。它们挡的是三类不同的失败，分属不同信任域：

| 闸 | 位置 | 挡什么 | 失败动作 |
|---|---|---|---|
| 闸1 | 模型推理侧 | 工具调用格式不合法、参数出枚举 | 把错误回灌重试（≤3 次） |
| 闸2 | 后端出参 | 组件不在白名单、props 不过 Schema、字符串带载荷 | **降级为文本** |
| 闸3 | 渲染前 | 前端包没注册这个版本、字节流被改过 | 不渲染，显示降级块 |

几处刻意的不对称：

- **闸1 可以重试，闸2 不能。** 闸1 失败时还没有任何副作用，重试是免费的；闸2 失败时数据已经查过、退款已经提交，只能换一种呈现方式。
- **闸2 降级时给的不是「出错了」，是同一轮工具执行产生的文字摘要。** 数据本身是对的，只是没穿上卡片 —— 用户损失的是观感，不是信息。
- **闸1 的重试对用户不可见。** 第一次尝试的文本已经流出去了，重试时不再重复推流，否则同一句话会冒两遍。
- **闸2 和闸3 用同一份 Schema 却各查一遍。** 因为信任前提不同：闸2 查的是「我们的代码有没有 bug」，闸3 查的是「我收到的这个字节流是不是服务端发的那份」。把闸2 当闸3 的替代，等于假设服务端到浏览器之间不可篡改。

## 4. 三条红线

**① 数据权限只认登录态**

`core/auth.ts` 里没有任何入参能让它返回别的用户。请求体里带了 `userId` 也不读 —— 那个字段在 `ChatBody` 里声明出来，就是为了让 code review 时一眼看到它被忽略了。

再往下，`core/data/order-service.ts` 的每个查询函数第一个参数都是 `sessionUserId`：**越权在函数签名层面就不可能发生**，因为压根没有「按传入 userId 查询」这个入口。

**② 金额服务端权威**

退款表单里的金额字段是只读的，`editable: false` —— 它的值不进表单状态，提交时也不带。用户改不了，模型更改不了。服务端 `submitRefund` 收到任何 `claimedAmountCents` 都只用来告警，金额一律以订单在业务系统里的值为准。

幂等做了两层，都落在**数据库**上而不是进程内存里 —— 请求维度靠一条部分唯一索引，业务维度靠查在途记录。为什么必须落在库里、以及它怎么跨进程验证，见 [§7 持久化](#7-持久化)。

**③ 全链路审计**

`correlationId` 从 `text_delta` 贯穿到 `done`。护栏面板里那个 ID 可以直接查回服务端 trace：

```
GET /api/trace?correlationId=msg_xxx
```

## 5. 生产就绪

协议对了不等于线上不炸。下面四个是这套架构上**真实会出事**的位置 —— 共同点是它们都不在 demo 的路径上，所以不专门做就不会被发现。

**① 超时与降级（不设超时 = 把可用性交给下游）**

模型调用 30s、工具调用 5s，都走 `withTimeout`（`core/runtime/timeout.ts`）。工具超时不是抛给用户看，是转成一句人话 + `degraded` 标记 —— 这一轮还没到闸2，数据没查到，能给的只有「稍后再问我一次」。

**② 熔断与限流**

`CircuitBreaker` 三态（closed / open / halfOpen），连续 3 次失败后 open 10s；**half-open 只放一个探针** —— 放一批进去等于没熔断，下游刚起来又被按死。限流是 `KeyedRateLimiter`（按 session 平分桶）+ `ConcurrencyGate`（全局并发上限）。

入口闸在 `core/gateway/guard.ts`。它必须**在 SSE 流内部**拿名额：连接数超限那条路径根本不会执行 `run`，名额放在外面就泄漏了。

**③ 预路由：不是所有输入都值得过一次模型**

「你好」「在吗」这类纯招呼，走 `core/runtime/router.ts` 的正则直出，不进模型。省的不只是钱 —— 闲聊占了客服流量的一大块，让它们排队等模型首 token，是拿最贵的资源做最不值的事。

判定用「只剩招呼词」而不是「包含招呼词」，尾部语气词（呀/啊/呢/哦…）先剥掉再比。`costLedger` 记的是 token 不是钱：价格会变，token 不会。

**④ 版本共存与灰度**

`RefundReasonChart@2` 是真的存在的一个新版本，只加了一个可选字段 `highlight`。选版走 FNV-1a 分桶（`core/runtime/rollout.ts`），**同一个 session 每次都落到同一版** —— 用随机数会让用户在同一轮对话里看到卡片变形。

关键点：Schema 校验是**按版本索引**的（`COMPONENT_VERSION_SCHEMAS[component][version]`）。如果还是「一个组件一份 Schema」，v2 信封会在闸2 被自己的校验挡下来 —— 灰度开关打开的那一刻全量报错。

自测里有两节专门管这件事。一节演练灰度本身：同样的 v2 信封，老包拒绝、新包渲染。另一节查**发版顺序** —— 灰度的真实事故不是分桶算错，是前端包里没人把 v2 写进渲染清单，于是开关打开的瞬间，闸3 把每一个 v2 信封都判成「版本未注册」，**全量用户看到的都是降级文本块：功能没坏，但没人看得到**。

所以断言写成：协议层能下发的每个版本，前端清单必须声明能渲染。这条断言不是摆设 —— 开发时它真的红过一次（清单还停在 v1），红的时候给的是「前端清单缺：RefundReasonChart@2 —— 先发前端包再开灰度」。

## 7. 持久化

会话和业务数据都在 `node:sqlite`（Node 22.5+ 内置，不引第三方依赖）。选它不是因为「够用」，是因为这一层**没有值得引入依赖的复杂度**：两张表、一个部分唯一索引。

真正值得写下来的是幂等键放在库里这件事。内存实现下，「这个键提交过没有」活不过进程重启 —— 演示时看不出来（重启一次数据就没了，没人会去验），但真实系统里进程天天重启，同一个幂等键在重启后返回的会是**第二笔**退款。

所以验证脚本要跨进程：

```bash
npm run check:persist
# 进程 A：写入 → 退出
# 进程 B：读同一个幂等键 → 拿到同一笔单据，库里只有一条
```

```sql
CREATE UNIQUE INDEX idx_refunds_idem
  ON refunds(idempotency_key) WHERE status = 'submitted';
```

`WHERE` 子句是有意的：只对成功单据生效。被风控拒掉的那次如果也占用键，用户换个说法再试就永远提交不上了。

## 8. 怎么验证

```bash
npm run check      # 一键跑完下面四步，CI 里跑的也是这条
```

拆开看，四步各自回答一个不同的问题，缺一个都有盲区：

```bash
npm run typecheck      # 类型还自洽吗
npm run selftest       # 172 项 —— 代码还按设计工作吗（挂了就是 bug）
npm run check:persist  # 幂等跨进程重启还算数吗（内存实现过不了这一步）
npm run regress        # 134 条分层测试集 —— 模型还选得准吗
npm run bench          # 时延实测（p50 / p95，不进 check）
```

selftest 的断言是「代码是否按设计工作」，挂了就是 bug。eval 的断言是「模型应该选对」，挂了可能是模型不行、也可能是工具描述写得不够清楚 —— 是质量问题，处理方式不一样，所以分开。

eval 分四层统计，因为失败的含义不同：

```
分层结果
  展示       34/34   100.0%
  操作       25/25   100.0%
  闲聊       33/33   100.0%
  对抗       42/42   100.0%
```

对抗层的期望写成「不许出现什么」而不是「应该出现什么」—— 攻击失败的正当姿势有很多种（降级文本、直接拒绝、走安全路径），只认一种会把正确行为判成错误。所以这一层的核心断言是 `noLeak`：别人的订单号、手机号、ID，一个字都不许出现在这一轮的任何出口上（文本、组件 props、事件流）。

### 上线门槛

评测跑完还会对着第四阶段那张指标表报一次数：

```
上线门槛（离线可测的部分）
  ✓ 意图识别准确率   100.0%   ≥   95%   107 条声明了期望
  ✓ 组件选择正确率   100.0%   ≥   95%   59 条有期望组件
  ✓ 工具调用成功率   100.0%   ≥   99%   闸1，81 次调用
  ✓ 组件渲染成功率   100.0%   ≥ 99.5%   闸3，79 个信封
  ✓ 降级比例           0.0%   ≤    5%   59 条想组件
```

一张列在文档里的门槛表，和一条会拦人的门槛，是两回事 —— 所以门槛没达标会让 `npm run eval` 直接退出码非零，不看人有没有注意到那一行。它和 `--strict` 各管一头：`--strict` 比的是**和上次**（防慢慢退步），门槛比的是**和绝对线**（防一直就不够好）。

口径上有两处刻意分开的地方：

- **意图准确率看工具调用，不看最终渲染。** 被闸2 降级成文本的那一刻，「模型想不想出组件」和「用户看没看到组件」就分家了 —— 混在一起算，会把降级记成意图错，而这是两个完全不同的故障（一个改 prompt，一个查闸门）。
- **对抗层不进意图准确率。** 它们大多不声明期望（攻击失败的正当姿势有很多种），算进来会让这个数字变成一个混合了「意图识别」和「攻击防御」的怪东西。

门槛没达标时会列出拖后腿的用例 id 和它期望/实际的组件 —— 光有一个百分比只能说明「有问题」，说不出「哪里有问题」。

**未测的部分每次都打出来**：CLS、含真实网络的 TTFB、任务完成率 / FCR / 人工转接率 / CSAT 都离线算不出来。写出来是为了别让人以为它们被测过了 —— 一个只报达标项的看板，比没有看板更危险。

**每次结果都落盘到 `eval-runs/`**，`--strict` 会和上一次对比，把「改好一个、改坏三个」直接变成非零退出码。一个只往 stdout 打印的评测，跑完就什么都没了 —— 它回答不了「刚改的那句 Prompt 到底修好了什么」。

CI（`.github/workflows/ci.yml`）跑的就是 `npm run check` 这一条命令，**和本地完全同一条** —— 不然会出现「本地过了 CI 挂」这种最消耗信任的失败。评测基线用 actions/cache 跨轮次累积，否则每次都是「第一次跑」，`--strict` 抓不到回归。

想看真模型：

```bash
LLM_PROVIDER=anthropic ANTHROPIC_API_KEY=sk-... npm run dev
npm run eval -- --provider=anthropic
```

mock 的 100% 是**基线**，不是成绩。真模型跑出来的数字和它的差值，才是「这一层被替换掉之后净影响多少」。

这件事要说清楚：**上面那个 134/134 不能证明意图识别准**，它证明的是这套协议和闸门在一条确定的路径上确实按设计工作。真模型路径本地跑不了（没有密钥），所以它是**未被测量**的，不是「也是 100%」。

## 9. 已知边界

这个仓库证明的是协议层的设计，不是一个可以直接上线的客服系统。真上线还差的：

- **会话存储换 Redis**。现在是 SQLite，多实例水平扩容时会话不共享（幂等已经跨进程了，会话还没有）。
- **审计换日志管道**。现在是本地 JSONL，Serverless 无持久卷。
- **闸2 的 Schema 校验换 ajv**。现在是手写的，故意保持在「一眼能读完」的规模 —— 但手写校验器本身是个风险面，生产环境换成 ajv 成本为零（用的是标准 JSON Schema 子集）。
- **限流的维度**。现在是按 session 分桶，真实系统要按用户 + IP + 租户三层，且阈值必须来自真实流量而不是拍脑袋。
- **CLS 没实测**。`npm run bench` 只覆盖服务端那一段时延，CLS 是浏览器的布局事实，Node 里算不出来（`scripts/bench.ts` 顶部写了为什么不算，以及浏览器里该怎么量）。
- **成本只是记账，不是管控**。`costLedger` 记了 token，`sessionBudget` 能查，但还没有「超了就降级到便宜模型」这条策略。

两个演进拐点，到了再动，**但也别等到出事才动**：

- 工具数 > 15 → 上 Tool Router（先按意图粗筛，再让模型在子集里选）
- 组件数 > 20 → 组件治理平台化（契约发布、版本兼容检查、渲染成功率看板）

这两条线不是写在文档里就算数的 —— 每次 `npm run selftest` 都会打一行：

```
· 拐点计数：工具 4/15（健康） · 组件 4/20（健康）
```

刻意**不判红**：跨过阈值是正常的业务增长，该做的是按计划升级，不是让 CI 挂。但一个每次都在屏幕上的数字，比一句躺在文档里的红线有用 —— 这类债的特征是「平时无感、到点雪崩」，唯一能防住它的就是让它定期出现在视野里。

## 10. 这笔投入值不值得

前面九节都在讲怎么做。这一节讲**该不该做** —— 一个技术方案如果没人算过账，评审时第一个问题就会卡在这里。

口径先对齐：这不是「从 0 上 AI 客服」，是在**已有纯文本 AI 客服**之上做体验升级。所以收益是**增量**（结构化场景的边际改善），不是「AI 替代人工」的全量。任何把 70% 自动化率套上来的算法都是错的。

**不作为的代价不是 0，是持续失血**：结构化查询本来能自助，纯文本给个链接用户还是转人工；退款操作路径长（对话→读文字→跳转→查找→提交），每多一步都在流失。

基准情景（行业中位数假设：日咨询 1 万次、GenUI 可覆盖子集 15%、该子集绝对转人工下降 12pp、单次人工 ¥6、单次增量模型成本 ¥0.05）：

| 项 | 结果 |
|---|---|
| 年减少转人工 | 65,700 次 |
| 年净节省 | ¥357,700 |
| 一次性研发（10 人月） | ¥300,000 |
| **回收周期** | **≈ 10 个月** |

盈亏平衡只需要一年减少 5 万次转人工 —— 基准情景已越过约 31%。

但这个数字**不该被当真**。三情景下回收周期是 3.6 个月 ~ 49 个月，跨度四倍以上，而最大的变量只有一个：**GenUI 到底能把复杂场景的转人工率降多少**。

这不是财务问题，是产品有效性问题 —— 只有 POC 的 A/B 能给出真实值。所以正确的投法是：**先批 30 万做 MVP + POC 把这个变量测准，达基准再追加；达不到就秒退回纯文本，沉没成本仅 30 万，且组件库和评测集是留下的资产。**

顺带回答两个会被问到的问题：

- **半年后模型升级要不要推倒重来？** 不用。三层解耦就是为这个准备的 —— 换模型只动工具层，组件注册表和 SSE 协议原样复用，是配置级而非重构级。
- **一年后要不要上 AG-UI？** 默认不上。它的价值在多 Agent、双向状态同步、复杂 human-in-the-loop；如果一年后客服还是「查询 + 单步操作」，上它就是过度工程。触发条件出现时再评估，届时组件注册表复用，不推倒重来。

> 本节所有金额是基于行业中位数假设的**测算，不是承诺值**，且未计入转化挽单、CSAT 等上行收益（保守处理）。真实决策必须用公司实际的咨询量、转人工率、坐席成本重算 —— ROI 对这几个数高度敏感。
